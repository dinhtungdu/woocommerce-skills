# WooCommerce pull-request and browser-evidence policy

Load only when preparing, publishing, updating, or recording evidence for a WooCommerce pull request.

Read `playbooks/opening-a-pr.md` from the installed `poteto-mode` skill. This policy overrides the playbook's body structure, readiness, and publication rules. Keep the WooCommerce template and draft-only authority below.

## Publication authority

- Follow the shared [non-personal repository authority](non-personal-authority.md). The task owner may create its draft after proportionate checks/review, and update its own draft with relevant ordinary pushes, factual title/body changes, and accepted sanitized evidence. Keep unfinished verification and open decisions explicit; preserve user-written prose and project template boundaries.
- Verified AI-review feedback such as CodeRabbit/Copilot may be addressed with in-scope fixes, ordinary pushes, evidence-backed replies, and resolution of AI-only threads. Recheck identity and participants before acting; human-involved threads remain on the user. This permits AI-feedback fixes on the task's own non-draft PR, not other non-draft body/evidence edits.
- Human communication and marking ready are on the user. Other consequential GitHub actions, including human replies/reviews, reviewer requests, merges, issue mutations, labels, force-pushes, and non-draft body/evidence edits, require an explicit request. The task owner performs external actions; specialist findings and agent approvals remain advisory.

## PR body, native attachments, and testing instructions

- Agents may supply a short, precise, diff-specific `--title` at initial draft creation; without one, the task heading is used. Agents may write the summary and description under `### Changes proposed in this Pull Request:` and revise their own prose on authorized updates. Write one short paragraph of 2–3 sentences explaining the problem and approach, grounded in the diff and verified evidence. Do not add summary bullets, subheadings, or a separate long description. Keep issue references on separate lines. Preserve existing user-written prose unless the user requests a rewrite.
- PR preparation uses the current exact task-branch PR body when one exists, otherwise the repository template. Editable content is limited to the agent-authored summary and description under `### Changes proposed in this Pull Request:`, `### Use of AI Tools`, the content between the testing-instruction markers for `### How to test the changes in this Pull Request:`, `Closes # .`, and `(For Bug Fixes) Bug introduced in PR # .`. Accepted public-safe/redacted verification images or videos may be added under `### Screenshots or screen recordings:`. Remove the testing-history section as required below. Preserve all other bytes and template boundaries.
- Always remove `### Testing that has already taken place:` and all its contents from generated WooCommerce PR bodies, including authorized updates to existing PRs. Remove through the next heading of the same or higher level, leaving that next heading intact, or through the end of the body. Do not preserve, fill, or replace this section. This exception does not expand publication authority.
- Always upload authorized PR screenshots and videos with [GitHub CLI native attachments](https://docs.github.com/en/github-cli/github-cli/attaching-files-with-github-cli). This overrides pstack's generic PR-tool preference for media attachments only; publication authority is unchanged. Do not substitute Amp links, local file URLs, another upload service, or a comment just to attach media.
- For an existing PR, re-read its current body immediately before uploading; for initial creation, use the repository template. Place local-file Markdown image references only in the screenshots section. Use `gh pr create --draft --body-file <file> --attach <media>` for initial creation or `gh pr edit <pr> --body-file <file> --attach <media>` for an authorized update. Repeat `--attach` for multiple files. Each reference must match its attached path so GitHub CLI rewrites it in place instead of appending media outside the allowed section. Put each video reference in its own paragraph to render a player.
- Read back the PR body and verify the GitHub-hosted media URLs, placement, and preservation of protected prose. An upload can partly succeed despite a nonzero exit status; inspect the body and uploaded assets before retrying. If native attachments are unavailable, report the blocker and retain the accepted artifacts instead of switching upload methods.
- AI disclosure names only exact provider/model identifiers and factual roles for implementation, review, testing, and PR preparation; retain truthful existing disclosures. No generic AI-review caveats, self-justifying disclaimers, or other filler. Keep substantive human-review requirements in review policy, not repeated PR prose.
- Use closing keywords only for a verified issue the PR resolves; otherwise use a related-issue reference or `N/A`. Fill the introducing PR only with verified evidence, `Unknown` when unestablished, or `N/A` for non-bug-fix changes. Never invent references or create an issue merely to fill the template.
- Contributor test copy includes only needed setup, actions, expected results, and limitations needed to execute the test. Do not append verification reports: environment inventories, pass counts, lint warnings, CI summaries, local tooling blockers, or lists of unrelated untested areas. Keep those in task evidence and the task-chat completion report, not the testing instructions. Keep internal auth, backups, hashes, diagnostics, recording, cleanup, and harness mechanics out.
- Reviewer testing instructions exercise the changed behavior through its actual user/developer interface, with observable expected results. Do not add automated suite runs (PHPUnit, Jest, lint, or type checks) as reviewer steps; those are author verification evidence. Include a targeted automated test only when necessary to reproduce a specific regression, explaining why and what result to expect. This applies to both the concise and detailed flows.
- Keep automated commands and their verified results in author verification evidence, separate from reviewer instructions.
- User-approved concise test lines are frozen. Lead may apply tiny exact staged prose corrections directly when no helper mutates; substantial drafting or evidence uses a separate scoped helper.
- Write two equivalent numbered, step-by-step test flows: a concise developer flow first, then an expanded newcomer/agent flow in one collapsed `<details>` with exactly `<summary>Detailed instructions</summary>`.
- Use a few short numbered steps in the developer flow. Each step gives the relevant action and observable expected result. Assume an existing development environment and WooCommerce knowledge; include only feature-specific prerequisites needed to run the checks independently. Omit repeated setup, obvious navigation, exhaustive viewport lists, and QA-report prose. For responsive changes, name the relevant breakpoint or range rather than every tested width. Avoid vague directions such as “test filtering” or “verify it works.”
- The detailed flow expands the same steps with exact setup, navigation, fixture requirements, values, and commands where needed. Keep the same order, coverage, and expected results; do not hide extra assertions or scenarios only in the detailed version.
- Adapt the checks to each PR's actual change and verification, not a fixed checklist. Use the shortest sequential path covering the changed behavior and relevant regression risks. Invent no fixtures, mutations, matrices, languages, or cleanup. Before handing off, check that a developer can run the concise flow without opening the details and that the detailed flow expands, rather than adds to, its coverage.

## Browser evidence

- Record a short real-browser screencast when interaction, timing, or a multi-step editor/frontend flow is clearer in motion, or when the user requests video. Decide during PR preparation; do not wait for a separate recording request when it materially helps review. Use screenshots for static visual changes and no browser video for non-UI changes. If recording is blocked, report the blocker and retain available evidence.
- Follow the contributor testing instructions and assert the shown results. State any setup done off-camera or steps not replayed; an existing-fixture demonstration is not a full test-flow recording. Retain raw capture and results separately from the polished final MP4. Use the bundled recording workflow (`references/recording-video.md` in the `woocommerce-verification` skill) for paced input, cursor feedback, HyperFrames finishing and exported-motion review; editing never replaces browser testing.
- Load `references/browser-evidence.md` in the `woocommerce-verification` skill and `references/browser-harness/README.md` in the `woocommerce-verification` skill only for browser work.
- Initial recording and evidence-only correction use a separate scoped helper with that bundled workflow; no external recording skill is required.
- No final recording before persisted passing dry run. Testing and recording are bidirectional: execution gaps correct instructions.
- Omit dedicated save/reload persistence passes unless persistence changed, realistic regression risk requires them, or user requested them. Saving remains allowed to expose frontend behavior.
- Every recording emits bounded Evidence metrics with UTC wall time/phases, revisions, preflight failures, recording attempts, categorized rework, primitive reuse, and rejected assertions. Retain the exact metrics line in task-local evidence and the native task completion report. Three-run trial is complete; do not extend ledger.
- Stage under task-local `tmp/prepare-pr/`; inspect and ingest through task-scoped the harness's accepted evidence workflow using flat artifact names. Maintain lessons, preflight results, metrics, harness, results, and media throughout success/failure. Reuse accepted verification screenshots and their result artifacts from `tmp/verification/` when preparing PR evidence; identify what each image proves and its ingested artifact name. Attach accepted media under the PR-body rules above only when authorized; otherwise report the accepted artifact to the user.
- Deliver accepted video files to the user only on request, through the route the user names; send the final MP4, not WebM, and verify delivery.
